jimmutable-core architectural design record

A source-derived record of the repository’s current architecture: an immutable domain-object and serialization kernel, extended by a cloud integration layer with environment-selected adapters for storage, search, Redis messaging/cache, and email.

Decision

Preserve a two-layer library architecture. The core JAR owns deterministic domain objects, validation, freezing, field containers, and explicit JSON/XML serialization. The cloud JAR depends on that model and supplies application-facing ports plus environment-specific infrastructure adapters. Runtime selection is centralized in CloudExecutionEnvironment.

Persisted and transmitted objects are modeled as StandardObject implementations. Immutable objects complete through a strict normalize → validate → freeze lifecycle. Serialization is deliberately explicit: each type writes its fields, reads from an ObjectParseTree, and is registered by a stable TypeName.

Cloud-capable domain objects opt into storage and search independently through Storable and Indexable. Infrastructure access is expressed through six ports—search, storage, queue, signal, email, and cache—with production/dev and stub implementations selected at startup.

Context and decision drivers

The repository supports Java applications that need value-like domain objects shared across persistence, search, servlet responses, queues, signals, and caches. Those objects must remain comparable and serializable without allowing collection aliases or iterators to mutate completed instances.

  • Deterministic data behavior: normalize and validate at object completion; make completed object graphs resistant to mutation.
  • Stable wire/storage forms: support JSON, pretty JSON, XML, and in-memory token buffers using the same object contract.
  • Infrastructure portability: keep application code pointed at small ports while switching local, AWS/Redis/Elasticsearch, or stub adapters by environment.
  • Operational reuse: centralize startup, type registration, heartbeat, logging, object caching, and uncaught-exception handling.
  • Testability: provide stub services for unit tests and name integration tests with the Maven Failsafe *IT convention.

Core class model

The central abstraction is behavioral rather than annotation-driven. A domain type implements its own comparison, normalization, validation, type name, field writer, and parse-tree constructor. Immutability is applied at the end of construction and propagated into collection wrappers.

Core invariants

  • complete() is a one-way boundary for immutable objects: normalize, validate, freeze, then mark complete.
  • FieldCollection and FieldMap guard every mutating path, including iterator mutation; null collection elements are skipped.
  • A completed immutable object returns itself from deepClone(); incomplete objects clone through token-buffer serialization.
  • Serialized object identity is a stable, simple TypeName, not a Java fully qualified class name.
  • Deserialization requires prior registration and a compatible constructor that consumes ObjectParseTree.

Serialization and object lifecycle

Lifecycle flow

From construction to round-trip reconstruction

Failure paths terminate in validation or serialization exceptions.

ObjectWriter delegates low-level tokens to Jackson-backed writers. Parser detects XML or JSON from the input prefix, or consumes a Jackson TokenBuffer, and builds a neutral tree. ObjectParseTree converts primitives, collections, maps, enums, stringables, and registered standard objects. JimmutableBuilder reuses this tree representation to clone and modify immutable objects without exposing setters on the object itself.

Cloud runtime and adapter selection

CloudExecutionEnvironment.startup(...) is the composition root. It validates application identity, creates Redis and the standard-object cache, selects adapters, registers core and cloud type names, starts heartbeat support, and installs the default uncaught-exception handler.

Storage and search participation

A Storable exposes a Kind, ObjectId, serialized form, and derived ObjectIdStorageKey. Storage adds caching, scanning, and threaded handlers around the concrete local-filesystem or S3 primitives. An Indexable exposes an index definition, document ID, and field-writing callback. One domain type can implement both—as StandardChangeLogEntry does—without coupling the core module to cloud infrastructure.

Consequences and trade-offs

Benefits

  • Immutable domain types are easy to share across threads, caches, queues, and API responses after completion.
  • The same explicit field contract drives JSON/XML persistence, deep cloning, builder edits, and messaging payloads.
  • Stable type names decouple persisted data from Java package refactors.
  • Infrastructure ports keep most application code independent of S3, Redis, Elasticsearch, and SES client APIs.
  • Stub startup provides a fast service-free test mode; integration tests remain opt-in.

Costs

  • Each domain type carries repetitive constructor, writer, comparison, equality, normalization, validation, freeze, and registration code.
  • Manual registration and explicit field readers make schema evolution safe only when developers maintain compatibility deliberately.
  • The global execution environment reduces wiring ceremony but introduces process-wide state and startup-order coupling.
  • The cloud JAR combines HTTP utilities, persistence, search, messaging, email, and operational helpers, producing a broad dependency surface.

Alternatives considered by this record

AlternativeWhy it is not the current baseline
Reflection/annotation-based serializationWould reduce boilerplate, but weakens the repository’s explicit wire contract and stable simple-name registry unless carefully constrained.
Dependency-injection containerWould improve instance scoping and test substitution, but changes the startup and access model used throughout cloud code.
One module per infrastructure capabilityWould narrow dependencies and release units, but requires a compatibility and migration plan for the existing single cloud artifact.
Java records plus a general object mapperWould simplify value objects, but does not directly reproduce the custom normalization, validation, freezing, type-name, XML, and builder semantics.

Observed risks and architectural debt

Reactor version split

cloud declares core:0.0.18 while the local core module is 0.0.19-SNAPSHOT. A root reactor build therefore does not represent a single aligned source baseline.

Parent POM split

Active modules disable parent relative paths and inherit external com.rws:rws-parent:0.0.6. The checked-in rws-parent:0.0.7-SNAPSHOT is not the active parent.

Duplicate Elasticsearch client

The cloud POM declares the same elasticsearch-java GAV twice at versions 8.17.0 and 8.19.12, making effective dependency resolution less obvious.

Global mutable startup state

The environment, identifiers, adapters, and object cache are static. Tests in one JVM must control ordering, and application code cannot naturally host multiple environments.

Class-initialization coupling

Some static domain metadata, including StandardChangeLogEntry.INDEX_DEFINITION, reads the current environment during class initialization.

Manual type registry

New persisted types are not deserializable until explicitly added to a register. Duplicate registration is allowed, so name collisions resolve by last registration.

Broad cloud release unit

Servlet, AWS, Elasticsearch, Redis, Apache POI, CSV, logging, and utility dependencies ship together even when a consumer needs only one capability.

Build-policy mismatch

The root POM manages Java 8 compiler settings while each active module directly compiles for Java 17; the direct module configuration currently wins.

Guardrails and follow-up decisions

  1. Keep core free of cloud-provider, servlet, Redis, Elasticsearch, and AWS dependencies.
  2. For every new immutable type, test completion, post-freeze mutation paths, JSON/XML round trips, comparison/equality, and type registration.
  3. Treat TypeName, field names, Kind, storage keys, and index definitions as versioned external contracts.
  4. Call CloudExecutionEnvironment.startup before loading environment-dependent classes; prefer passing a port into new code where practical.
  5. Align module versions and parent resolution in a dedicated build ADR before changing release behavior.
  6. Resolve the duplicate Elasticsearch client declaration and record one compatibility matrix for Java, Jetty, Elasticsearch, Redis/Jedis, and AWS SDK.
  7. Consider separate cloud capability modules only through a compatibility-preserving migration ADR.
