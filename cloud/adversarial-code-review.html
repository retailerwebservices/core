Resolution status

Corrected in the current uncommitted working tree: findings 1, 3, 4, 5, 6, and 7.

Reads now fail closed except for an explicit not-found or non-string result; region comes from the AWS SDK provider chain; creation is name-only with shared validation; mutations use typed rejected/unknown outcomes and retry tokens; updates use the idempotent PutSecretValue operation; owned clients close through an idempotent adapter and environment shutdown hook; and the stub fails closed during pending deletion without promising that asynchronous purge has completed at the recovery-window boundary.

Still open: finding 2 (non-production environments use real AWS services) and finding 8 (the process-global STUB service can leak mutable state between test classes). The source excerpts and line numbers in the finding cards remain the historical evidence that prompted the remediation.

High

Secret reads fail open on every AWS failure

readSecret turns every exception into the caller’s default. Missing data, denied access, expired credentials, throttling, wrong-region access, network failure, SDK defects, and an unexpected null response are indistinguishable.

Concrete failure scenarioAn AdRocket service starts with an expired workload role. Instead of reporting an authorization failure, the API returns null or a plausible fallback. Startup may proceed with a broken or obsolete credential, obscuring the security-boundary failure.
Recommended remediationReturn absence only for an explicitly supported not-found or non-string case. Propagate or wrap authorization, throttling, transport, and unexpected failures. Prefer a required-secret method or typed result that cannot silently degrade.
2
High

DEV and INTEGRATION are wired to real AWS with destructive operations

Local and integration startup construct the same AWSSecretsManager used in staging and production. The interface also exposes create, update, and delete operations. There is no account guard, environment prefix, read-only wrapper, or non-production endpoint enforcement.

Concrete failure scenarioA developer has broad credentials in the default profile and runs an integration workflow with a production secret ARN. The code accepts it and can update or schedule deletion of the real secret.
Recommended remediationUse SecretsStub, LocalStack, or an explicitly isolated AWS account/endpoint for DEV and INTEGRATION. Split runtime reads from administrative lifecycle operations, and enforce an environment namespace or allow-list.
3
High

Normal runtime wiring ignores the AWS region provider chain

The no-argument adapter always targets us-west-2. Although a caller can directly inject a custom client, CloudExecutionEnvironment always calls the no-argument constructor, so application configuration cannot override the region through the supported composition root.

Concrete failure scenarioA workload deploys in us-east-1 with AWS_REGION=us-east-1. The service still queries us-west-2; issue 1 then converts the resulting lookup or access failure into a fallback.
Recommended remediationAllow SecretsManagerClient.builder().build() to use the standard region provider chain, or require region/client configuration in startup.
4
Medium · expanded analysis

The advertised ARN contract is false for creation

The interface-level statement applies “names or ARNs” to every operation. That is true for AWS operations that address an existing secret through SecretId, but it is not true for CreateSecret: creation requires a new secret name. The implementation maps the same undifferentiated secret_id argument to CreateSecretRequest.name.

Why this is more than documentation wording

  • The type system cannot express the distinction. A caller sees one String accepted by all four methods and reasonably reuses an ARN obtained from configuration.
  • The actual cause is hidden. AWS rejects the ARN as a name, but the broad catch returns only false. The caller cannot tell invalid identifier form from access denial or an existing secret.
  • The stub gives a false positive. SecretsStub.createSecret accepts any non-blank string, including an ARN, so a test can pass while production fails.
  • The abstraction leaks provider vocabulary. A supposedly provider-neutral interface explicitly promises ARN support, coupling its general contract to AWS without accurately modeling AWS’s operation-specific rules.
Caller stores an ARN
Passes ARN to createSecret
Adapter assigns ARN to name
AWS rejects it; caller receives only false
Recommended remediationAt minimum, document createSecret as name-only and existing-secret operations as name-or-ARN. A stronger design uses separate types such as NewSecretName and SecretIdentifier, with shared validation used by both AWS and stub adapters.
5
Medium

Mutation booleans misrepresent indeterminate outcomes

A network timeout after AWS accepts a request is reported as false, which sounds like “nothing changed.” Separate caller retries may encounter an existing secret, create another version, or find deletion already scheduled.

Recommended remediationExpose operation-specific results or typed exceptions. Preserve stable request tokens when callers must retry across method invocations, and document delete as an asynchronous state transition.
6
Medium

The default AWS client has no ownership or close lifecycle

The adapter can allocate its own closeable SDK client, but it is not AutoCloseable and cannot express whether it owns an injected client. The composition root suppresses resource warnings and provides no shutdown method.

Recommended remediationTrack client ownership, implement AutoCloseable, and close owned clients from an environment shutdown hook. Do not close externally injected clients unless that ownership contract is explicit.
7
Medium

Stub deletion semantics materially diverge from AWS

The stub removes immediately and allows immediate recreation. The AWS adapter schedules deletion using the provider default recovery window; a scheduled secret cannot be read or normally recreated until restored or permanently deleted.

Recommended remediationModel a pending-deletion state in the fake, or explicitly label it a simplified fake and cover recovery-state workflows with a higher-fidelity integration test.
8
Medium · expanded analysis

The global stub can leak secret state between test classes

This is an interaction defect across four individually reasonable choices: CURRENT is static, startup is allowed only once, STUB installs one mutable SecretsStub, and the common test base catches subsequent startup exceptions. The result is one process-wide secret map for every test class that accesses the global execution environment.

How the leak occurs

First StubTest subclass calls startup
CURRENT receives one SecretsStub
Later subclasses catch “startup already called”
All classes keep using the original mutable map
  • Order dependence: a test creating adrocket/api-key can cause a later create test to return false, or make a missing-secret test unexpectedly find data.
  • Cross-class contamination: JUnit creates test instances, but the secret state lives behind a static process singleton and therefore outlives those instances.
  • The current unit test does not exercise the risky path: SecretsStubTest constructs a fresh stub directly. It never accesses CloudExecutionEnvironment.getSimpleCurrent().
  • Parallel execution magnifies the problem: ConcurrentHashMap prevents structural corruption, not semantic interference between tests sharing identifiers.
  • The catch is overly broad: StubTest treats every startup RuntimeException as ignorable, which can conceal initialization failures beyond the expected “already started” condition.
Recommended remediationAdd an explicit test-only reset/replace hook for the environment or inject a fresh ISecrets per test. Alternatively, give SecretsStub a controlled clear()/seed lifecycle and call it in setup/teardown. Test the exact global access path and stop swallowing unrelated startup exceptions.

Optional improvements

Rotation-aware caching or read-once injection. Uncached retrieval adds latency, cost, throttling exposure, and a dependency on Secrets Manager availability. Prefer bounded caching or resolve required secrets once during startup, while preserving rotation behavior.
Broader negative-path tests. Add service-specific exceptions, region selection, ARN/name validation, owned-client closing, composition-root wiring, shared-stub isolation, and pending-deletion scenarios. The existing seven tests prove request construction but not these operational boundaries.
Review exception logging. Lines 63, 83, 105, and 125 log raw exception objects. No explicit secret value is interpolated, but confirm SDK/custom-client exception messages cannot carry sensitive request context.
Use the imported AWS BOM consistently. The dependency-management BOM already fixes SDK version 2.31.55, so the explicit module version is redundant and can drift during future upgrades.

Confirmed-correct behavior

No direct secret-value logging found. Log statements use fixed operation messages and do not interpolate secret_value.
Recoverable deletion is correctly requested. Neither forced deletion nor a custom recovery window is set, so AWS applies its service default recovery window.
Core request mappings are correct. String values map to secretString, existing-secret operations use secretId, and reads use the current version by default.
